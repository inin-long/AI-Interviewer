# 订单系统一致性与缓存治理手册

## 1. 事务消息与 Outbox

订单服务处理创建请求时，先校验调用方提供的 `requestId`。订单表对租户编号与 `requestId` 建立唯一约束，重复请求直接返回第一次处理结果。业务事务同时写入订单记录和 Outbox 事件，禁止在数据库事务中直接调用消息中间件，因为远程调用无法与本地事务形成同一个原子提交边界。

Outbox 发布器按主键游标批量领取尚未投递的事件。领取动作记录 Worker 和租约过期时间，发送成功后更新投递状态；进程崩溃后，其他 Worker 可以重新领取过期任务。消息发送采用至少一次语义，因此消费者必须使用事件编号建立消费记录，在同一事务中完成去重记录与业务更新。

发布失败时使用指数退避重试，并设置最大重试次数。超过阈值的事件进入失败队列并触发告警。补偿任务定期扫描长时间未完成的 Outbox 记录，结合订单状态判断是重新投递、人工处理还是关闭事件。监控指标至少包括积压数量、最老事件年龄、发布延迟和失败率。

## 2. Redis 缓存一致性

数据库是订单事实来源，Redis 只承担查询加速。写请求提交数据库事务后发布缓存失效事件，消费者删除对应缓存；不使用“先更新缓存再更新数据库”，避免数据库事务回滚后缓存保留错误值。

删除缓存失败时，事件处理器会重试。系统同时安排短延迟的二次删除与周期补偿扫描，以降低网络抖动造成的脏数据窗口。缓存值设置随机抖动的过期时间，避免大量热点键同时失效。读取未命中时通过单飞请求合并限制回源并发，仍然以数据库结果重建缓存。

对于强一致要求高的订单状态页面，可以在写入后短时间绕过缓存，或携带版本号比较缓存数据与客户端已知版本。任何缓存策略都必须配套命中率、回源量、热点键、重建耗时和失败次数监控。

## 3. 故障恢复检查清单

1. 验证相同 `requestId` 重放不会创建第二张订单。
2. 验证数据库提交成功而消息发送失败时，Outbox 补偿能够重新投递。
3. 验证消费者收到重复事件时只执行一次业务变更。
4. 验证 Redis 删除失败后，重试和补偿任务最终清理旧值。
5. 验证 Worker 在领取任务后崩溃，租约过期后任务能够恢复。
6. 验证告警中包含租户、订单、事件编号和可追踪的 Trace ID。

## 4. 面试评估要点

候选人需要明确区分数据库原子性与跨系统最终一致性，能够解释幂等键、唯一约束、至少一次投递、消费者去重、重试退避、死信处理和人工补偿之间的关系。只回答“使用 MQ 保证一致性”并不充分，还应说明失败发生在提交前、提交后、发送中和消费中时分别如何恢复。
